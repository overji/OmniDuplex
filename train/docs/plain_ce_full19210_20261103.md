## 数据快照与审计

- 原始数据：19,210 QA、4,925 视频；旧 5,000 QA 全部保留，无精确 QA 重复，文件均存在。
- 完整 ffprobe/metadata 时长清单保存在本次 inputs 快照中，最长视频约 415 秒。原 metadata 仅有旧 1,268 视频，未被覆盖。
- 固定旧视频划分；新增视频按 SHA256(`42:` + 视频路径) 的确定性阈值分配验证集，约 20%。
- 实际准备：**15,524 训练 QA / 34,445 个可评分 response；3,631 验证 QA / 8,065 个可评分 response**。
- 排除 55 QA / 227 个可评分 response：52 条回复超出视频末尾、3 条调度冲突。窗口不修改，回复不截短。
- 旧验证集中有效的 **996 QA** 单独保留为 previous 子集；其余为 added 子集。每轮全验证集和两个子集复用同一遍验证前向。
- `sampling_omissions` 均为零。输入快照、审计和 prepared 数据均记录哈希；准备文件在等待期被修改会阻止启动。
- 与 AOI-Bench 的视频文件名交集为零；这是 UUID/路径检查，不是不同 UUID 下的内容指纹去重结论。

## 配置

八卡 DP，单卡 microbatch 1，梯度累计 2，有效 batch 16；普通 CE、学习率 1e-6、两轮、完整视频、全部 response、问题后空闲秒沉默监督、65536 token、ZeRO-2 CPU optimizer。保持长度桶 120、CPU 激活预算 128 GiB/rank、GPU 保留预算 4 GiB/rank、预留 12 GiB。每 50 步保存，保留一个编号 checkpoint 与 final。TensorBoard 开启，W&B 关闭。

预计 **1942 次参数更新**。按数据量和平均视频时长增幅粗估 6–8 天，须用新数据前 20 次更新重新估算。不要把更多 QA 直接等同于需要提高学习率或上下文上限。

## 自动顺序与失败保护

1. 等待前一轮两个 benchmark 和 Judge 正常到终态、相应进程退出及八卡释放。单条 Judge 最终失败允许记录为 incomplete；服务崩溃或终态缺失会阻止启动。
2. 八卡 profile：从 train 中选择八条最长、文本最多、response/chunk 最多的代表 QA，覆盖 PR/RTD/Agent。验证一次有限更新、无 QA 排除、实际完整序列长度和 GPU 显存，并记录主存可用量下界。profile 不保存权重；主存预留至少 16 GiB。
3. profile 通过后从基座重新启动正式训练；不使用 profile 更新后的参数。
4. 全部八个 rank 的最终保存及步数核验成功后，导出外部模型；0–3 卡跑 AOI-Bench，4–7 卡跑 OmniPro，之后四卡 Judge。

任何 profile 失败都停止衔接并留下原因，不自动提高预算、放宽窗口或截断视频。普通 CE 下新增首次/后续开口、回复前后沉默等诊断不改变损失数值和梯度。
